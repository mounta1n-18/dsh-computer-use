# 从一次 1000+ 题的浏览器自动化里提炼的 9 条

> 背景：2026-10-29 ~ 10-30，在一所高校的在线教学平台（THEOL/优慕课，JSP + GBK）上完成
> 10 份在线测试、1000+ 道题，其中 5 份卷子 100+ 题，最长一份 317 题。
> 工具：`huashu-chrome`（驱动用户真实 Chrome 的 MCP）+ 本插件的 `computer_use`。
> 下面的每一条都对应一次真实的翻车或一次真实的省时间，不是推演。

---

## 1. 先找接口，再想操作

任何"列表 + 表单"的站点，**一次 GET 拿全量、一次 POST 写一条**，永远比点界面稳、快、可核对。

- 点一次单选，触发的是同一个 `saveAnswer` POST，但要多付一次整页渲染（这站 10–25 秒）。
- 读数：317 题的卷子，走接口 **13 分钟**交卷；走点击，估算几小时且无法逐题核对。
- 判据：如果页面上每个"操作"背后都是一个 XHR/fetch/表单提交，那它就是接口，不是 UI。

## 2. 成功率必须"读得出来"，不能"看出来"

可断言的东西：返回体字节数、HTTP 状态、页面上的状态格文本、列表页的"已交卷"字样。
不可断言的东西："看起来变了"、"应该成功了吧"。

这次能无人值守跑完，靠的就是一条硬判据：
**返回体 > 500 字节 = 保存成功；≈192 字节且含跳转脚本 = 被拒（答案过长）**。
没有这条，1000 次写入里只要错 3 次就是灾难，而"看截图"永远发现不了。

## 3. 单次执行预算 < 20 秒

**症状**：一条命令卡 32 秒超时，连着卡 5 次，人以为脚本挂了。

**根因链**（实测日志）：

```
后台标签页 → Chrome 把 setTimeout 压到 ~1 次/分钟
        → 为守住节奏改用忙等 while(Date.now()-t0<8000)
        → 忙等占满渲染进程主线程
        → 后续注入排队，每条命令 32s 超时
        → 把"重试"当解药 → 每条又各卡 32s
        → 页面内一个 8 分钟的循环 → 连续 9 分钟没有任何命令能返回
```

**规则**：

- 一条命令一件事，单次 `eval` 预算 **< 20 秒**；
- 页面里只放**状态**（`window.__prog = {done, fail, last}`），不放循环；
- 节奏由**宿主侧**控（sleep / 定时任务），页面永远保持"随时可对话"；
- `TIMEOUT` **两次就停手**，先 `tabs list` 看现场，而不是连发同一条命令；
- 十分钟级的活儿交给宿主进程，浏览器只做"一次一小步"。

## 4. 原生弹窗不是页面元素

`confirm` / `alert` / `prompt` 是**浏览器 chrome 层**，不是 renderer 里的 DOM：

- 它一弹，页面 JS 线程停摆 —— `fetch`、`eval`、内容脚本注入全部排队，表现为"整条链路卡死"；
- CDP 的 `Input.dispatchMouseEvent` **打不到**它，坐标点击也没用；
- 唯一正解是 `Page.handleJavaScriptDialog`（CDP），或者人在真窗口上按一下。

推论：**自动化方案必须先问"这站会不会弹原生窗"**。会弹，就得有 dialog 通道，
否则所有批量写入都会在第一次限流时集体瘫掉。

## 5. 节奏是站点协议的一部分，不是异常处理

"请不要过于频繁答题"这类弹窗不是 bug，是服务端的正常回答。

- 把它写进主循环（每 N 题停 M 秒），而不是写进 `catch`；
- 实测安全区：**5–6 秒/题**；低于 2 秒连续 10 题左右必触发；
- 触发后不要重试同一条路径（会再触发），先降速再续。

## 6. 编码是两个方向的事

页面是 GBK 时：

- **读**：`fetch` → `arrayBuffer` → `new TextDecoder('gbk')`，不能直接 `.text()`；
- **写**：POST body 必须是 **GBK 的百分号编码**。用 `URLSearchParams` 发 UTF-8 会"提交成功但库里是乱码"，
  而且**不报错**。

**验证方式只有一个**：写一条 → 立刻回读 → 逐字比对。别等批量灌完再回读。

## 7. 对齐要用双键，不要用序号

"答案按题库序对到了卷面序"是这次最大的返工（用户当场发现"题和题的内容对应啊"）。

- 序号会变：题库序、卷面序、分页序是三套东西；
- 唯一稳的键是 **`qid` + 题干文本**，两者都一致才写；
- 写完抽检 3–5 题回读，比"全部写完再检查"便宜一个数量级。

## 8. 平面分工：网页用浏览器平面，窗口用桌面平面

| 需求 | 该用谁 | 为什么 |
|---|---|---|
| 读页面结构、点元素、填表 | 浏览器平面（CDP / 可访问性树） | 元素有 ref，不怕滚动和重排 |
| 原生弹窗、地址栏、下载条 | 桌面平面（真窗口键鼠） | 这些不在 renderer 里 |
| 切窗口、调窗口大小、看整屏 | 桌面平面 | 浏览器平面只管标签页 |
| 大批量数据 | `fetch` / `network`，别点 | 一次拿全量 |

代价也要算：桌面平面会**抢焦点**、要授权、截图贵（一次全屏 ≈ 300–400 token）。
所以"能用元素级操作就别动桌面平面"。

## 9. 先用最小样本走通全链路

这次的正解顺序是：拿 10 题的小卷（实验 3/3）把"读—写—回读—交卷—出分"整条链走通，
再上 317 题的大卷。

反面教材：先在大卷上试编码，结果整批 UTF-8 乱码只能重发。
**任何"不可逆 + 大批量"的组合，都必须先有一次小样本的完整闭环。**

## 附：给工具作者的四条

1. **弹窗要有 API。** 内部实现了 `Page.handleJavaScriptDialog` 却不暴露，等于让使用者回到"人肉点弹窗"。
2. **超时要分层。** `PAGE_BUSY`（页面忙，可等）和 `TIMEOUT`（真死）是两件事，混在一起模型只会盲目重试。
3. **长任务要有一等公民。** 页面内队列 + 短轮询应该是内置能力，而不是每个使用者自己发明 `window.__prog`。
4. **失效句柄要自愈。** `NO_TAB` / `STALE_SNAPSHOT` 这类错误，工具自己重扫一遍成本极低，
   丢给模型就是十几次往返。
