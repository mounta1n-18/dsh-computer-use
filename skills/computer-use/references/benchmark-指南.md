# 给 computer-use / cu.py 做 benchmark 的指南

> 2026-10-11 一整天实测踩出来的，全是教训。短。

## 一、设计

### 场景：先看"起始状态确定不确定"，再谈覆盖面

| 场景 | 覆盖能力 | 步数稳定性 |
|---|---|---|
| T1 计算器：打开算 123×456、报结果、关掉 | 启动应用、键盘输入、读结果、收尾 | **稳（5 步）** |
| T2 微信收发：给文件传输助手发一条消息 | 识图、点击、输入、发送核验 | **不稳（13~28 步）** |
| T3 系统设置：快速设置面板把亮度调到 50% 再改回 | 面板操作、滑块拖动、恢复原值 | 较稳（9 步） |

**选场景的第一标准不是覆盖面，是「起始状态是否确定」。**
T2 的起始状态每次都变（微信停在会话列表 / 聊天面板 / 窄屏折叠），同一提示词跑出 13~28 步
——**这种场景不能用来判定优化好坏**，要么先做状态归一化，要么只当"能跑通就行"。

### 提示词：必须是真实用户口吻

- ✗ 错：把"别复述画面、别做任务外的事、launch 用中文名、别点面板右下角的齿轮、收尾 focus-cc"
  全写进提示词。那是在考**模型能不能照抄详细规格**，不是在考技能——**过拟合**。
- ✓ 对：`打开计算器，算一下 123×456，把结果告诉我，然后关掉计算器。`

**所有操作规范固化在技能里；提示词只留用户真会说的话。**
唯一允许写进提示词的是**控制变量本身**（例：`用上面的搜索框找到它`），不写操作技巧。

### 「能用」怎么判

用**会话日志的真实时间戳**，不用感觉。每个场景 = 一个**全新上下文的 subagent**
（它的 session id 就是 runId），跑完从它的会话文件里算各阶段耗时。

## 二、一致性（控制变量）

| 变量 | 怎么控制 |
|---|---|
| 模型 | 固定不换 |
| **上下文** | **每个场景一个全新 subagent**。同一个 agent 连跑多轮，上下文越跑越长、越跑越慢 |
| 起始状态 | 每轮跑前/跑后都复位；**不能复位的场景不能用** |
| 机器负载 | 用 **ms / 输出token** 判断两轮是否可比（实测漂在 4.3~7.8） |
| 比较方式 | 同一时段的数才能横比；跨时段的只当过程记录 |

**负载判据**：两轮 ms/tok 差 20% 以上，墙钟就不可比，只能看步数和 token。

## 三、判据

**确定性的（当闸门）**
- **步数** ← 最稳，直接等于往返次数
- **输出 token** ← 主成本，实测 5~10 ms/token
- **工具调用参数字符数** ← 模型为一次调用要写的样板量

**非确定性的（只当结论）**
- 墙钟 —— 受机器负载影响，同一场景能差一倍

## 四、护栏（防改坏）

- `perf/bench/guard.py` 钉住 cu.py 的功能契约：输出结构、退出码、错误码表、最小化/遮挡行为。
- **护栏写「契约检查」，别写「数量比对」**——加两个错误码，数量比对的护栏就误报 FAIL。
- 任何改动后跑一次；FAIL 就不许继续。

## 五、踩过的坑（都要避免）

1. **在提示词里写规范** = 过拟合，测的不是技能。
2. **同一个 agent 连跑多轮** = 上下文污染，后一轮天然更慢。
3. **起始状态不复位** = 噪声压倒信号（T2 就这样废了一轮）。
4. **换技能目录和数据采集放同一个程序** = 中途中断会留下旧版技能（真发生过，靠快照救回）。
5. **用 PowerShell 的 `-match` 读 UTF-8 中文** = 一定乱码，误判文件内容。用 grep 工具。
6. **只测一次** = 单次不可信；墙钟至少 3 轮取中位。
